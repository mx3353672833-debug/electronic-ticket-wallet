# 每次发布都更新公告

网页右上角的「更新记录」读取 `src/data/releases.json`，本机和服务器构建共用这一个来源。不另写一份容易过时的网页文案，也不从 Git 提交自动生成未经核实的功能宣传。

## 发布步骤（所有维护者与 Agent）

1. 确认上次已上线的 Git 提交。只有用户实际能用到的已完成变化才写入公告；待办、数据源调研和未验证功能不能写成已上线。
2. 在 `src/data/releases.json` **最前面追加**版本、真实发布日期、简短标题和 1–6 条用户能看懂的变化。旧记录保留，不能为发布新版本而覆盖旧内容。只改文档且不部署网站时不必升网页版本。
3. 同步升级 `package.json` 与 `package-lock.json` 的根版本。首次引入公告时使用 v0.2.0；此前未分别编号的内测更新汇总在 v0.1.0，不能补造不存在的 Git tag。
4. `npm run check:release -- --since <上次线上提交>`。此检查要求升版本、保留旧公告；如果历史提交还没有公告文件，允许第一次补建。普通 `npm run build` / `build:server` 也会检查公告、版本、日期和条目格式一致性，但无法自行判断漏写了哪项功能，不能省略人工核对及 `--since` 检查。
5. 运行 `npm test`、`npm run test:server`、`npm run test:routes`、`npm run lint`、`npm run build` 和 `npm run build:server`，在桌面、手机检查入口、滚动、关闭／Escape、关闭后地图与筛选保持不变。
6. 程序与公告作为同一个构建发布，保留可回滚的上版程序，不覆盖任何用户数据。上线核对当前版本与公告文字，确认旧记录仍可查看；成功后将部署提交、验收结果和未完成事项写入项目交接记录。

公告不含真实票据数量、路线、用户邮箱、邀请码、密码或服务器运维资料。它是产品更新说明，不是私人操作日志。公告不自动弹窗、不发邮件，不要求阅读后才允许使用。
